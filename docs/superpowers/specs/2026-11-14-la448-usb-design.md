# LA448 over USB: design

## Intent

Control a Sinbosen LA448 over its USB port, alongside the existing LA548/UDP
support. Reaching the unit over UDP means joining its own Wi-Fi network,
which costs the host its internet connection; USB avoids that.

## What a read-only probe established (2026-11-14)

- The LA448 enumerates as a vendor HID device: VID 0x0483, PID 0x5750,
  usage page 0x8C, 64-byte input and output reports, no report ID.
- It speaks the LA548 command protocol unchanged. Each request frame is
  zero-padded into one 64-byte output report; a reply longer than 64 bytes
  continues across consecutive input reports, zero-padded after the tail.
- `READ_LOCK_STATE`, `HAND_SHAKE`, `READ_GROUP` and `GET_USER_NAME` all
  answered. `READ_GROUP` returned 2464 bytes and decodes with the existing
  DA0408X profile (4 inputs, 8 outputs). 39 reports arrived in ~0.96 s.
- Replies carry version byte 0x0F (the LA548 sends 0x0A / 0x13). The client
  does not match on that byte.
- The device sends nothing unsolicited.

Not established: any write over USB, and how a request longer than one
report (the 2048-byte FIR coefficient write) must be split.

## Goals

- `usb` (first matching unit) or `usb:<serial>` is accepted wherever an IP
  address is today: `Client`, every CLI command, the UI connect box.
- All request-safety logic (send pacing, reply matching, quarantine,
  keepalive, link state) is shared between UDP and USB, not duplicated.
- UDP behaviour and the dependency-free base install are unchanged.

## Non-goals

- Renaming the package or CLI.
- Running the audio-loopback `hardware_test/` suite against the LA448.
- USB hot-plug handling beyond reporting the link down.

## Anti-goals

- Sending any frame the UDP path would refuse, or any speculative write, to
  learn the USB behaviour.

## Approaches

1. **Pluggable link under `Transport` (chosen).** `Transport` keeps framing,
   pacing, matching, quarantine and keepalive, and talks to a small link
   object (send bytes / receive bytes / close). `UdpLink` holds today's
   socket code; `HidLink` pads and chunks into 64-byte reports.
2. **Separate `UsbTransport` class.** Simpler to write, but copies the
   request-safety logic that exists because of real incidents, and the two
   copies would drift.
3. **Local UDP-to-HID bridge process.** No client changes, but a second
   process to run and no way to address a unit by serial.

## Decisions

- `hidapi` is an optional `usb` extra, imported only when a `usb` address is
  used; a missing package gives a clear install hint.
- Requests longer than 64 bytes are refused locally over USB (revised after
  review: the original plan was to split them into consecutive reports, but
  that guess would have been reachable from `write-fir-coefs` untested).
- A unit is matched on VID/PID and the `AudioSystem` product string, because
  0483:5750 is a stock STMicro ID shared by unrelated devices.
- Docs record the LA448 findings and mark USB writes as unverified until
  each is confirmed with `--verify`.

## Left to the builder

Link interface shape, test doubles, and where address parsing lives.
